## Acceptance sequence

1. **Install:** User A runs `./install-macos.sh --account-pair` from the reviewed pinned artifact on Mac A. Select a disposable allowed folder containing a unique non-secret marker. Verify private keys stay local, terminal/GUI remain disabled, and no other installation is changed. Compare the installer's device ID/fingerprint with the tested build's diagnostics.
2. **Pair account:** The installer opens exactly `https://<authorized-staging-host>/pair/claim`, without query or fragment. User A authenticates, copies the local one-time code into the form, verifies account/provider/device/fingerprint, and checks file access consent. The installer must complete signed-device verification before reporting success. Verify one active owned device and the expected identity tuple through metadata-only evidence; no private keys or credentials are inspected.
3. **Containment/negative cases:** Check browser address/history URLs and redirect destinations for credential absence without recording auth parameters. Confirm no body logging/custom telemetry captures pairing credentials. These are live-environment observations, not guarantees from `no-store`. In disposable separate attempts: close without confirming; replay the code/confirmation; change authenticated accounts after review; omit consent; wait past code/consent expiry; and attempt a second active Mac. Each must fail without binding another account/device. Check browser back/refresh/resubmit and double-tap behavior. The code and confirmation are strictly one-time, so a second submission is expected to show a refusal; the first may already have succeeded. Let the Access session expire between review and confirmation: the browser should refuse to send the form body to the login redirect (`form-action 'self'`), and nothing may bind. Record whether the example `BETA_ENROLL_RATE` (5/min per address) leaves enough headroom for start + code page + review + confirmation, and how a 429 looks to the user. Cancelling the local code dialog does not cancel the server session: the shown code stays valid for up to five minutes. Confirm the dialog wording tells the user never to share it. Use synthetic local fixtures for credential inspection where possible; never paste a live credential into ChatGPT.
4. **Connect ChatGPT:** On the fresh account, use the actual supported authenticated integration route offered by ChatGPT. Check OAuth discovery and sign in to the same Astra account. Record whether it is a developer connection or an approved published plugin. If normal ChatGPT chat on iPhone does not expose/call the integration for this account, record the exact client/policy limitation and stop this acceptance path; do not replace it with another interface. Voice remains a separate optional test, not implied by chat success.
5. **Read effect:** In normal ChatGPT chat on iPhone, request: “Use Astra to read `mobile-acceptance.txt` in my approved test folder and tell me its marker.” Verify the returned non-secret marker matches Mac A. Metadata-only audit must identify A's device and the read tool. With approved account/Mac B available, verify B cannot read A's marker and that caller-supplied device hints cannot redirect a call.
6. **Write effect:** Request creation of `mobile-result.txt` containing a new non-secret acceptance marker inside the approved folder; give any requested ChatGPT write confirmation. Verify its exact bytes on Mac A and absence on Mac B/owner Mac. A terminal/GUI request must remain denied on both server and local boundaries. Do not enable either capability to complete the test.
7. **Revoke:** Prepare offline SQL with `node relay/scripts/beta-invite.mjs revoke-device --owner OWNER_ID --device-id DEVICE_ID --out NEW_REVIEW_DIRECTORY`, using the exact verified staging owner/device metadata. This command prepares SQL only. Review its owner/device predicates and target D1 database; apply only with explicit staging revocation authorization. A fresh tool call, an existing-chat call and signed agent reconnect/status must deny access; no additional file change is permitted. Disconnecting a ChatGPT integration alone does not prove server-side device revocation. Record revocation metadata and the denied follow-up, then perform only authorized cleanup.

## Documentation checked 2026-10-02

- [OpenAI authentication](https://developers.openai.com/plugins/build/auth): MCP authorization uses discovery and authorization-code/PKCE, then authenticated MCP requests. Mac pairing remains a separate setup binding.
- [OpenAI connection testing](https://developers.openai.com/plugins/deploy/connect-chatgpt): developer-mode availability depends on account/workspace policy; test tool selection, authenticated calls and write confirmations. This does not establish iPhone availability for a specific fresh account.
- [OpenAI plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines): mobile reliability is a publication requirement, not evidence that this unsubmitted integration is approved or universally available.
- [Cloudflare Managed OAuth](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/): the origin validates the forwarded Access assertion. Preserve the reviewed single application identity boundary for browser claim and MCP; actual fresh-account continuity still requires testing.
- [Cloudflare JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/): validate the signature, configured issuer and application audience. No new trust is granted to caller-supplied identity fields.
- [Cloudflare D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/): batch statements form a transaction and roll back on failure. SQLite adapter checks are useful but do not replace the real D1 runtime gate.
- [Cloudflare log settings](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/settings/methods/get/): query redaction is a logging setting; do not assume query strings are secret. The implementation removes credentials from generated URLs and does not change live settings.
- [RFC 8628 sections 3.2–3.3](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.2): separate client polling credentials from the user-entered code and require informed authorization. This custom flow borrows that separation; it is not advertised as RFC 8628 compliant.
